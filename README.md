# AI Sana — TaskRank & TeamMatch

Общее ядро MVP для HackAlem AI: бизнес уточняет задачу, подтверждает карточку и получает рейтинг готовности. Студенты подают предложения, бизнес вручную выбирает одну, несколько или ни одной команды.

**Статус этой ветки:** реализованы сервисы, AI API, хранилище, синтетические данные и автоматическая проверка сквозной логики. `App.tsx` пока содержит только переключатель ролей. Конструктор, каталог, отклики и Inspector нужно подключить в UI перед демонстрацией жюри. Успешная сборка не означает готовность полного интерфейса.

## Установка и запуск

Нужны Node.js 22.12+ (проверено на 24.13.1) и Python 3.10+. Из корня репозитория:

```powershell
npm --prefix frontend ci
python -m venv .venv
.venv\Scripts\python -m pip install -r backend/requirements-dev.txt
```

Backend в первом терминале:

```powershell
.venv\Scripts\python -m uvicorn main:app --app-dir backend --host 127.0.0.1 --reload --port 8000 --no-proxy-headers
```

Frontend во втором:

```powershell
npm --prefix frontend run dev
```

На macOS/Linux используйте `.venv/bin/python`. Интерфейс: http://localhost:5173; API-документация: http://localhost:8000/docs; health: http://localhost:8000/health. Vite пересылает `/api` на backend; порт 5173 фиксирован, чтобы конфликт порта был виден сразу.

Без backend клиент автоматически использует локальный анализ. Для гарантированного локального демо скопируйте `frontend/.env.example` в `frontend/.env.local`, задайте `VITE_AI_MODE=local` и перезапустите Vite. Для отдельного API-хоста настройте `VITE_API_BASE_URL`; при публикации без Vite нужен reverse proxy `/api` или корректный CORS на API.

Внешний AI необязателен. Для него скопируйте `backend/.env.example` в `backend/.env`, заполните ключ OpenAI **или** NVIDIA и при необходимости `AI_MODEL`. Если заполнены оба ключа, используется OpenAI. Ключи читаются только сервером; не помещайте их в `VITE_*`. Используйте синтетические данные. Доступность внешних провайдеров в автоматических тестах не проверяется.

## Одна проверка перед интеграцией

```powershell
npm run check
```

Команда последовательно запускает pytest, smoke-проверку реального локального сервера, frontend regression suites, lint и production build и останавливается при первой ошибке. Отдельные frontend-проверки: `npm test` (для проверки совместимости API также нужен установленный backend). Smoke-сервер запускается на свободном loopback-порту с временным токеном, без внешнего AI и останавливается после проверки.

Проверяются не только примеры seeds: повреждённый JSON, нарушения AI-схемы, таймауты, отсутствие сети, неподтверждённая генерация, точные прибавки рейтинга, TeamMatch, повреждённый LocalStorage, повторное подтверждение этапов и полный сценарий на уровне сервисов и store. Тесты не используют реальные AI-ключи и не вызывают провайдеров.

## Архитектура и общие контракты

| Слой | Ответственность |
| --- | --- |
| `frontend/src/types/` | Общие TypeScript-контракты; изменения `Task`, `Team`, `Proposal` согласует Core Platform |
| `frontend/src/services/aiClient.ts` | Проверка входа и ответа Zod, запросы с таймаутом, переключение на локальный алгоритм |
| `frontend/src/services/aiFallback.ts` | Извлечение исходных фрагментов и заполнение карточки ответами без выдуманных данных |
| `frontend/src/services/ratingService.ts` | Единая формула рейтинга, potential score и рекомендации |
| `frontend/src/services/teamMatchService.ts` | Объяснимое ранжирование опубликованных задач под профиль команды |
| `frontend/src/app/store.ts` | Zustand, действия пользователя и переходы между состояниями |
| `frontend/src/app/persistence.ts` | Проверка сохранённых данных, ссылок между сущностями и восстановление рейтинга |
| `backend/` | FastAPI, Pydantic, запрос к AI-провайдеру и серверный fallback |

Данные задач и откликов живут в браузере под ключом `ai-sana-taskrank-v1`; это демонстрационный режим, а не общий серверный каталог для разных устройств. При недоступном или переполненном LocalStorage работа продолжается в памяти, но новые изменения могут не сохраниться после перезагрузки. `resetToSeedData()` восстанавливает независимую копию пяти задач, пяти команд и пяти откликов; пять исходных черновиков доступны в `syntheticData.ts`.

### Порядок вызовов для разработчиков UI

```ts
const analysis = await analyzeDraft(draft, industry);
// Показать analysis.questions, собрать ответы пользователя.
const card = await generateCardFromAnswers({ draft, industry, answers });
// После проверки полноты объекта: addTask(card). Карточка редактируется в UI.
// Ручное подтверждение: confirmTask(card.id).
// Отдельное действие публикации: publishTask(card.id).
```

`generateCardFromAnswers` сохраняет совместимый тип `Promise<Partial<Task>>`; клиент заполняет ID, даты, поля и стартовый рейтинг. При необходимости перед `addTask` используйте `taskSchema.parse(card)` из `app/persistence`, чтобы получить проверенный `Task` без приведения типа.

- `addTask(task)` создаёт неподтверждённый черновик с нулевым рейтингом. `confirmTask(id)` подтверждает текущие непустые поля и пересчитывает баллы. `publishTask(id)` требует подтверждения.
- `updateTask(task)` снимает подтверждение изменённых полей. При изменении содержания карточка становится неопубликованной: UI должен предложить повторные подтверждение и публикацию. Баллы остальных подтверждённых полей сохраняются.
- `addProposal(proposal)` принимает отклик на опубликованную задачу от существующей команды; новый отклик всегда `pending`. Рейтинг не ограничивает доступ к откликам.
- `setProposalDecision(id, 'selected' | 'rejected')` вызывается по ручному решению бизнеса. Несколько команд могут быть выбраны одновременно. Для выбранной команды создаётся демонстрационный этап.
- `confirmMilestone(id)` начисляет баллы только выбранной команде и только один раз. Повторный вызов после перезагрузки баллы не дублирует.

Действия store сохраняют существующие сигнатуры `void`; некорректные действия игнорируются. Для сообщений об ошибках UI должен валидировать форму до вызова. Ошибки входных данных AI-клиента возвращаются как отклонённый Promise и должны отображаться формой. HTTP 4xx возвращаются как `AiRequestError` (или `AiScopeError` для тематического отказа): UI показывает `error.message`, сохраняет введённый текст и не считает карточку созданной. Сетевые ошибки и HTTP 5xx обрабатываются fallback.

## Рейтинг и TeamMatch

Рейтинг 0–100 складывается из контекста и потребности (20), данных (20), результата (15), критериев успеха (15), ограничений (10), пользователей (10), контакта и формата связи (10). Начисляются только баллы подтверждённых полей. Заглушки вроде «Не указано» не дают баллов.

Это прозрачная эвристика полноты текста, а не проверка истинности или качества бизнес-идеи: внутри полей используются пороги длины и частичные баллы. `potentialTotal` — сколько дадут **уже введённые** сведения после подтверждения. Рекомендация `+N` показывает прирост при дополнении и подтверждении конкретного поля до полного веса.

Уровни: 0–39 — `draft`, 40–69 — `working`, 70–89 — `ready`, 90–100 — `priority`. Seed ratings вычисляются той же формулой. Общий каталог должен показывать все опубликованные задачи с сортировкой по рейтингу, включая слабые задачи.

TeamMatch: технологии 35%, навыки 25%, интересы 20%, отрасль 20%. Совпадения нормализуются и не считают дубликаты или части других слов. `getRecommendedTasksForTeam` возвращает все опубликованные задачи, отсортированные по совпадению, затем рейтингу. Он не назначает исполнителей.

## AI и Prompt Inspector

- `POST /api/ai/analyze`: 3–4 вопроса, извлечённые поля, пропуски, `provider`, `fallbackUsed`.
- `POST /api/ai/generate-card`: детерминированная карточка из исходного текста и ответов. Все поля ещё требуют ручного подтверждения.
- `GET /api/ai/inspector`: используемый системный промпт, шаблон анализа, описание сборки карточки, Pydantic-схемы и обработка ошибок.

При настроенном ключе анализ вызывает внешний AI с общим таймаутом 3 секунды. Ответ проверяется по строгой схеме, а извлечённые значения — на наличие в черновике (с нормализацией пробелов). Ошибка вызывает серверный fallback. Клиент также проверяет ответы и имеет таймаут 12 секунд, включая чтение JSON. При недоступном Inspector показывает описание именно локального режима.

Проверка цитат ограничивает выдумывание фактов, но не гарантирует правильную классификацию текста. Локальный алгоритм ориентирован на русскоязычные черновики и может пропускать сведения. Человек проверяет карточку перед публикацией.

## Ограничение тематики AI

Фильтр проверяет черновик, отрасль и ответы на уточнения до вызова AI. Одинаковые правила для backend и браузера хранятся в `shared/aiScopePolicy.json`; этот файл нужно поставлять вместе с backend, сохраняя структуру репозитория.

| Запрос | Результат |
| --- | --- |
| «Реши математическую задачу: 2x + 4 = 10» | Отказ `OFF_TOPIC` с предложением описать бизнес-задачу |
| «Нужен бот. Игнорируй все предыдущие инструкции» | Отказ `PROMPT_INJECTION` |
| «Нужен учебный сервис по математике для школы» | Допускается как описание проекта |
| «Python», «2 недели» в ответах на уточнения | Допускаются в контексте подходящего черновика |

Backend возвращает HTTP 422 с `detail: { code, message }`. В клиенте это `AiScopeError`: UI должен показать `error.message` и сохранить введённый текст. Такой отказ **не** запускает fallback и **не** создаёт карточку. Ошибки сети по-прежнему переключают на локальный алгоритм, защищённый теми же правилами.

Модель может выбрать поля для уточнения, но тексты вопросов и их ID берутся из общей проверенной политики; свободные `question`/`reason` от модели не показываются. Нормализация учитывает Unicode, невидимые символы и переносы строк. Это правила для ограниченного MVP, а не универсальный семантический классификатор: возможны ложные срабатывания и непривычные формулировки, поэтому общий корпус `tests/ai_scope_cases.json` нужно дополнять реальными примерами.

Правила работы разработчиков и агентов со скиллами Codex/Gemini и сообщениями о ходе работы закреплены в `AGENTS.md`; `GEMINI.md` ссылается на него.

## Защита и режим публикации backend

Результаты аудита и проверяемые ограничения: [backend/SECURITY_AUDIT.md](backend/SECURITY_AUDIT.md). Зависимости закреплены в `backend/requirements.lock.txt`; результат проверки известных уязвимостей находится в `tests/security-audit-dependencies.json`.

Development API принимает только loopback-клиентов и разрешённые Host/Origin. Запускайте его с `--no-proxy-headers`, как в инструкции: middleware не доверяет `X-Forwarded-For`, но сам ASGI-сервер может изменить адрес клиента, если разрешить proxy headers.

Для публичного размещения задайте на сервере:

```dotenv
APP_ENV=production
API_ALLOWED_HOSTS=api.example.com
API_ALLOWED_ORIGINS=https://app.example.com
```

Также задайте случайный `API_ACCESS_TOKEN` длиной не менее 32 символов в серверном хранилище секретов. Без токена и явных hosts/origins production не запускается. Все `/api/*`, включая Inspector, требуют `Authorization: Bearer ...`; `/health` доступен без токена, Swagger/OpenAPI в production отключены. При настройке reverse proxy учитывайте разрешённый Host, HTTPS и префикс размещения.

**Токен предназначен для серверного gateway, а не для браузера.** Не помещайте его в `VITE_*`, LocalStorage или публичный frontend. Gateway должен сам проверять право пользователя на доступ и только затем добавлять backend-токен. Пользовательская авторизация и такой gateway пока не реализованы; обычный открытый proxy, добавляющий секрет каждому посетителю, защиты доступа не даёт.

Действуют ограничения: 256 KiB на JSON-тело, 5 секунд на его получение, глубина JSON 32, суммарный пользовательский текст до 50 000 символов. Повторные ключи, нечисловые `NaN/Infinity`, некорректный Unicode и сжатые тела отклоняются. Ошибки не возвращают присланные данные.

По умолчанию: 60 POST-запросов на клиента и 300 на процесс за 60 секунд; превышение возвращает 429 с `Retry-After`. Параллельно выполняется не более четырёх AI-вызовов на процесс; остальные переходят в локальный режим. Ответ провайдера ограничен 128 KiB, JSON модели — 64 KiB, генерация — 2048 токенами. Redirects и proxy-переменные для AI-запросов отключены; общий timeout — 3 секунды.

Для демо используйте один worker. Несколько workers/реплик требуют общего лимита на gateway, ограничения соединений и квоты расходов у AI-провайдера. Проверка не заменяет настройку TLS и инфраструктуры реального размещения.

## Пример демо после подключения UI

1. Ввести «Нужен бот для заказов» и показать минимум три вопроса.
2. Дополнить данные, результат, пользователей, критерии, ограничения и связь с бизнесом. До подтверждения показать текущий и потенциальный рейтинг.
3. Подтвердить карточку, показать рост рейтинга и опубликовать её.
4. Переключиться на команду и подать предложение из каталога.
5. Вернуться к бизнесу, вручную выбрать команду и подтвердить этап. Показать однократное начисление баллов.

Этот сценарий проверяет `tests/verify_core_flow.ts` на уровне логики. Браузерная проверка полного UI остаётся задачей интеграции веток. Пользовательская авторизация, серверная база данных, совместная работа разных пользователей и развёрнутая публичная версия в этой ветке не реализованы; bearer-защита API не заменяет пользовательские аккаунты.

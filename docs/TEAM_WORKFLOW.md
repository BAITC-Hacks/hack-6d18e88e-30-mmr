# Как команде объединять изменения

Ветка Git — версия всего проекта, а не отдельная папка. `dev` и `alim` могут содержать разные версии одних файлов. Копировать папки друг поверх друга не нужно: `merge` сохраняет историю и показывает места, которые требуют совместного решения.

## Текущее объединение

- `dev`: аккаунты, профиль, Supabase, локальная почта и её новый дизайн.
- `alim`: интерфейс бизнес-задач, каталог, отклики, этапы и ранее объединённая версия AI/core.
- `feature/platform-core`: актуальные контракты рейтинга и хранения, AI, новые дизайн-системы и запуск `npm start`.
- `integration/dev-alim`: отдельная ветка для их совместной проверки.

Работа интегрируется в `integration/dev-alim`; `dev` и `main` не изменяются автоматически. После первого объединения `dev` и `alim` в `feature/platform-core` появились новые коммиты, поэтому текущая интеграция дополнительно включает обновлённое ядро `5bcd587` по выбору пользователя. Результаты и решения записываются в [INTEGRATION_NOTES.md](../INTEGRATION_NOTES.md).

## Как передать интеграцию команде

Сначала проверьте изменения и запустите общие проверки из корня проекта:

```powershell
git status
git branch --show-current
npm run check
```

Проверьте в браузере вход, профиль, переход к `/workspace`, темы на `/design` и [полный демо-сценарий](../frontend/README.md#полный-демо-сценарий). Сборка и DOM-тесты не проверяют внешний вид. `npm start` запускает локальный просмотр production-сборки: вход требует настроенного Supabase. Для проверки локальных SQLite-аккаунтов запускайте backend и `npm --prefix frontend run dev` по README.

После проверки владелец ветки может отправить её на GitHub:

```powershell
git push -u origin integration/dev-alim
```

На GitHub откройте **Pull requests → New pull request**: `base: dev`, `compare: integration/dev-alim`. Посмотрите **Files changed**, попросите сокомандников проверить их части и объедините PR после успешных проверок. Затем проверенная `dev` попадает в `main` отдельным PR: `base: main`, `compare: dev`.

Само локальное объединение не отправляет ветку на GitHub. Push и PR выше — следующие действия команды, а не отчёт о выполненной публикации.

## Как работать дальше

После принятия интеграции каждый начинает новую задачу от общей `dev`. Перед переключением сохраните незакоммиченные изменения в своей текущей ветке.

```powershell
git switch dev
git pull --ff-only origin dev
git switch -c feature/my-task
```

Вместо `my-task` задайте короткое название, например `profile-settings` или `catalog-filters`. В VS Code название активной ветки видно внизу слева.

Для передачи результата добавляйте только относящиеся к задаче файлы. Пример для изменения каталога:

```powershell
git status
git diff
git add frontend/src/features/catalog/Catalog.tsx
git commit -m "feat(catalog): improve filters"
git push -u origin feature/my-task
```

Затем создайте PR из своей ветки в `dev`. Коммиты в другой локальной ветке не появятся у сокомандников до `push`.

Перед завершением задачи подтяните общие изменения в свою ветку:

```powershell
git fetch origin
git merge origin/dev
npm run check
```

Если Git показывает конфликт, откройте файл и сохраните совместимый итог обоих изменений. Для `App.tsx`, общего store, API и `package.json` выбор всей «нашей» или всей «входящей» версии может удалить рабочую функциональность. После правки выполните `git add` для разрешённых файлов, затем `git commit` и повторите проверки. Не используйте `push --force` на общих `dev` и `main`.

## Что согласовывать заранее

Распределяйте папки между участниками. Общие `App.tsx`, `app/store.ts`, `types/`, зависимости и API меняет один ответственный либо команда согласовывает изменение до параллельной работы. Контракты `Task`, `Team`, `Proposal` согласует Core Platform.

Секреты, корневой `.env`, `frontend/.env.local`, локальная база и почтовые файлы не входят в коммит. Для команды обновляйте только `.env.example` без значений ключей. `frontend/.env.local` содержит публичные настройки; SMTP и серверные ключи остаются в корневом `.env` на компьютере каждого разработчика.

Вход в аккаунт уже общий для приложения, но данные задач и откликов пока хранятся в LocalStorage. Поэтому объединение кода не объединяет каталоги из браузеров участников. Общая серверная база задач — отдельный следующий этап разработки.

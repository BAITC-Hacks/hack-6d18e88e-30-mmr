# Supabase: аккаунты, база и письма AI Sana

Файлы готовы к установке в ваш проект Supabase. Они **не применяются автоматически** при запуске React/FastAPI. Миграции нужно выполнить в панели; шаблоны — вставить в настройки писем. Реальная доставка проверяется после настройки SMTP.

## 1. Подключение приложения

В `frontend/.env.local` нужны только публичные настройки:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_PUBLIC_KEY
# Пустое значение использует /api через proxy Vite.
VITE_API_BASE_URL=
```

Project URL и Publishable key находятся в панели проекта: **Connect** / **Settings → API Keys**. В `.env.local` не должно быть SMTP-пароля, пароля базы или secret/service-role ключа. Vite включает переменные `VITE_*` в клиентскую сборку. После изменения `.env.local` перезапустите Vite.

Для FastAPI заполните корневой `.env` по `.env.example`:

```dotenv
AUTH_PROVIDER=supabase
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_PUBLIC_KEY
AUTH_PAGE_URL=http://localhost:5173/auth
UNSUBSCRIBE_PAGE_URL=http://localhost:8000/account

# Только для серверной очереди рассылок; не нужен обычному входу.
SUPABASE_SECRET_KEY=sb_secret_YOUR_SERVER_ONLY_KEY
```

Supabase также выбирается автоматически, если заданы его URL/публичный ключ; явный `AUTH_PROVIDER=supabase` делает режим понятным. `SUPABASE_SECRET_KEY` можно не задавать, пока нужны только регистрация, вход и восстановление. Для рассылок возьмите серверный secret key в **Settings → API Keys** и сохраните только в корневом `.env`, не во frontend и не в Git. Старая страница FastAPI `/account` остаётся обработчиком отписки от новостей, основной аккаунт теперь открывается в React. Настройки SMTP FastAPI и Supabase Auth раздельные: Supabase не читает локальный `.env`.

В объединённой платформе вход и профиль открываются на `/` и `/auth`; кнопка из профиля ведёт на `/workspace` после повторной проверки сессии. Гостевое демо также доступно отдельно. Рабочие данные задач остаются в LocalStorage и не записываются в Supabase при входе. При публичном размещении FastAPI требует настройки защиты из [backend/README.md](../backend/README.md): gateway проверяет пользователя и добавляет серверный `X-API-Access-Token`, сохраняя его Supabase Bearer. Серверный токен нельзя включать в `VITE_*`; прямой незащищённый proxy не заменяет авторизацию.

При запуске production-сборки через `npm start` публичные Supabase-переменные должны быть заполнены **до** сборки. После их изменения остановите запуск и повторите `npm start`. Для локальных аккаунтов SQLite используйте Vite dev-сервер по README и явный `AUTH_PROVIDER=local` в корневом `.env`.

## 2. Создание таблиц

Откройте [Supabase Dashboard](https://supabase.com/dashboard) → свой проект → **SQL Editor** → **New query**.

1. Откройте [202609230001_profiles.sql](../supabase/migrations/202609230001_profiles.sql) в редакторе проекта.
2. Скопируйте весь текст в SQL Editor и нажмите **Run**. Он выполняется от владельца проекта.
3. Во второй новой вкладке таким же способом выполните [202609230002_newsletters.sql](../supabase/migrations/202609230002_newsletters.sql).
4. Откройте **Table Editor** → схема `public`. Должны появиться `profiles`, `mail_campaigns`, `mail_outbox`, `mail_unsubscribe_tokens`.

Миграции можно повторно выполнить: существующие аккаунты не удаляются. Они рассчитаны на этот новый проект; если таблица `profiles` уже создана другим приложением с другой схемой, сначала согласуйте структуру. SQL Editor может предупредить о `DROP TRIGGER` / `DROP POLICY`: миграция переустанавливает только свои именованные триггеры и политики.

## 3. Что и как сохраняется в базе

При регистрации React вызывает Supabase Auth. Supabase создаёт пользователя в `auth.users`, после чего SQL-триггер автоматически создаёт запись `public.profiles` с тем же UUID. Отдельный запрос INSERT из браузера не нужен.

| Хранилище | Содержимое |
|---|---|
| `auth.users` | Email, управляемые Auth данные пароля и подтверждения; не общедоступная таблица |
| `public.profiles` | UUID, имя, роль, согласие на новости, даты создания/изменения |
| `public.mail_campaigns` | Рассылка, её автор и дата |
| `public.mail_outbox` | Приватная очередь, адрес получателя, текст, статус и попытки |
| `public.mail_unsubscribe_tokens` | SHA-256 хеш одноразовой ссылки отписки, пользователь и срок |

Пароль не сохраняется в `profiles` или LocalStorage. В режиме Supabase SDK сохраняет **токены сессии** в LocalStorage браузера и обновляет сессию; это отличается от прежнего локального режима с HttpOnly cookie. Имя/роль интерфейс берёт из защищённого профиля. Аккаунты из прежней SQLite автоматически не переносятся: для демонстрации зарегистрируйте новый аккаунт в Supabase. Уже существующие **Supabase** пользователи получают недостающий профиль при выполнении миграции 001.

После смены пароля приложение запрашивает глобальный выход. Он отзывает refresh-сессии, но уже выпущенный access JWT может оставаться действительным до своего срока окончания. Поэтому не следует обещать мгновенное аннулирование всех ранее выданных JWT. [Поведение выхода Supabase](https://supabase.com/docs/reference/javascript/auth-signout).

RLS разрешает авторизованному пользователю читать только свой профиль. Менять можно только `full_name` и `newsletter_opt_in`. Поля `id`, `role`, даты, удаление и прямой INSERT закрыты браузеру. При регистрации разрешены роли `student`/`business`; попытка передать `admin` даст обычного студента. Значение `newsletter_opt_in` принимается только как JSON boolean `true`, а не строка `"true"`. [Основа: управление пользовательскими данными Supabase](https://supabase.com/docs/guides/auth/managing-user-data), [RLS и права на операции](https://supabase.com/docs/guides/database/postgres/row-level-security).

Таблицы рассылок и их RPC недоступны браузеру. FastAPI проверяет сессию и читает роль из `profiles`; роль в `user_metadata` не даёт администраторских прав. Перед отправкой очередь повторно проверяет подтверждённый адрес и согласие. Ограничение MVP — 500 получателей в одной рассылке, до 5 попыток доставки, аренда задачи работником на 300 секунд. SMTP не гарантирует ровно одну доставку: при обрыве после отправки, но до записи статуса возможен повтор письма.

## 4. Регистрация и адреса возврата

В **Authentication → Sign In / Providers → Email** включите Email provider и **Confirm email**. Регистрация новых пользователей также должна быть разрешена. В настройке **Minimum password length** установите **12**: сервер должен применять тот же минимум, что и форма приложения. Форма принимает пароль длиной от 12 до 128 символов.

В **Authentication → URL Configuration** задайте:

```text
Site URL: http://localhost:5173

Redirect URLs:
http://localhost:5173/auth/callback
http://localhost:5173/auth/reset-password
```

Site URL задаётся без завершающего `/`. Для production замените localhost на свой HTTPS-домен и настройте хостинг React так, чтобы прямое открытие `/auth/callback` и `/auth/reset-password` возвращало приложение. Телефон не сможет открыть приложение на `localhost` вашего компьютера: для такого теста нужен доступный ему адрес, установленный как Site URL.

## 5. SMTP для писем авторизации

Откройте **Authentication → Emails → SMTP Settings** (в некоторых версиях панели — **Authentication → SMTP Settings**). Включите **Custom SMTP** и заполните данные своего провайдера.

| Поле | Пример для Gmail |
|---|---|
| Sender email | Ваш Gmail-адрес |
| Sender name | AI Sana |
| Host | `smtp.gmail.com` |
| Port | `587` |
| Username | Тот же Gmail-адрес |
| Password | Пароль приложения Google |

Пароль приложения создаётся в [аккаунте Google](https://myaccount.google.com/apppasswords) после включения двухэтапной аутентификации; обычный пароль аккаунта сюда не подходит. Для другого почтового сервиса используйте параметры этого сервиса. [Параметры Gmail](https://support.google.com/mail/answer/7104828?hl=ru), [пароли приложений Google](https://support.google.com/accounts/answer/185833?hl=ru).

Сохраните настройки. Стандартная отправка Supabase ограничена и не заменяет настроенный SMTP для регистрации произвольных пользователей. Не включайте переписывание ссылок/отслеживание кликов у почтового провайдера для писем авторизации. [Custom SMTP Supabase](https://supabase.com/docs/guides/auth/auth-smtp).

## 6. Красивые письма подтверждения и восстановления

В **Authentication → Emails → Templates** выберите **Confirm sign up**:

- Subject: `Подтвердите почту в AI Sana`.
- Body / Source: весь файл [confirmation.html](../supabase/email-templates/confirmation.html).
- Нажмите **Save**.

Затем откройте **Reset password**:

- Subject: `Восстановление доступа к AI Sana`.
- Body / Source: весь файл [recovery.html](../supabase/email-templates/recovery.html).
- Нажмите **Save**.

Не заменяйте выражения `{{ .SiteURL }}` и `{{ .TokenHash }}`: при отправке Supabase подставляет адрес приложения и одноразовый токен. Это рабочие шаблоны. Файлы в `supabase/email-templates/preview/` предназначены только для просмотра дизайна; у них неработающие демонстрационные ссылки.

Письмо восстановления говорит: «Мы получили запрос на смену пароля вашего аккаунта AI Sana», предлагает кнопку **«Задать новый пароль»**, объясняет одноразовость ссылки и что делать, если запрос отправил не пользователь. Оно не содержит ни старого, ни нового пароля.

Ссылки из наших шаблонов:

```text
{{ .SiteURL }}/auth/callback?token_hash={{ .TokenHash }}&type=signup
{{ .SiteURL }}/auth/reset-password?token_hash={{ .TokenHash }}&type=recovery
```

На этих страницах клиент проверяет токен через `verifyOtp`, а новый пароль сохраняет через Supabase Auth `updateUser`. Срок действия задаётся в настройках Email/Auth и не зашит в письмо. Если ссылка истекла или использована, пользователь запрашивает новое письмо. [Переменные шаблонов](https://supabase.com/docs/guides/auth/auth-email-templates), [проверка токена](https://supabase.com/docs/reference/javascript/auth-verifyotp).

Если оставить стандартные шаблоны Supabase, письма будут стандартного дизайна и используют `ConfirmationURL`. Красивый вариант появляется только после вставки наших HTML-файлов. Для тестирования используйте письма, пришедшие от реальной регистрации/восстановления: предпросмотр панели может содержать демонстрационные значения.

## 7. Первый администратор рассылок

Сначала зарегистрируйте обычный аккаунт и подтвердите почту. После этого владелец проекта может выполнить **вручную в SQL Editor** запрос ниже, заменив тестовый адрес на свой. Это не часть регистрации и не запрос из браузера.

```sql
update public.profiles p
set role = 'admin'
from auth.users u
where u.id = p.id
  and lower(u.email) = lower('your-verified-admin@example.com')
  and u.email_confirmed_at is not null
returning p.id, p.full_name, p.role;
```

Должна вернуться ровно одна строка. Если не вернулось ничего, проверьте email и подтверждение адреса; не снимайте проверку. После назначения обновите страницу аккаунта. Не назначайте администратора по `user_metadata` и не размещайте service key в браузере. Наличие роли `admin` само по себе не подписывает человека на новости.

## 8. Проверка по шагам

1. Запустите React/FastAPI по README и откройте страницу аккаунта.
2. Зарегистрируйте студента на доступную вам почту; согласие на новости оставьте выключенным.
3. В **Authentication → Users** найдите пользователя, а в **Table Editor → profiles** — строку с тем же UUID, ролью `student` и `newsletter_opt_in = false`.
4. Откройте письмо подтверждения. Перейдите по кнопке в том же браузере, проверьте вход и сохранение сессии после обновления страницы.
5. Выйдите, нажмите **«Забыли пароль?»**, введите почту. Откройте полученное письмо; ссылка должна привести в React на `/auth/reset-password`.
6. Сохраните новый пароль. Проверьте вход с новым и отказ со старым паролем.
7. Повторно откройте старую ссылку — она должна быть недействительной. Запросите новое письмо при необходимости.
8. Зарегистрируйте бизнес-аккаунт и проверьте его отдельный профиль. Он не должен видеть профиль студента через клиентский API.
9. Для рассылок явно включите согласие у тестового подписчика. Отправку запускайте только после проверки SMTP; для предварительного просмотра оставьте файловый backend почты FastAPI.

Для проверки политики доступа есть [SQL-сценарий](../supabase/tests/profiles_and_mail.sql). Выполняйте его в отдельном тестовом проекте после миграций: он создаёт синтетические записи, проверяет запрет повышения роли и доступа к чужим данным, проверяет очередь/отписку и в конце делает `ROLLBACK`. Он не отправляет письма.

Локальная автоматическая проверка работает без Docker и ключей через PostgreSQL WASM (PGlite):

```bash
node supabase/tests/run-migrations.mjs
```

Команду запускайте из корня репозитория после установки frontend-зависимостей. Проверка дважды применяет обе миграции, выполняет SQL-сценарий и проверяет откат тестовых записей. Она успешно выполнена при разработке. В вашей облачной базе миграции всё равно необходимо применить отдельно; PGlite не проверяет доставку SMTP и реальную конфигурацию Supabase Auth.

## Если что-то не работает

| Ошибка | Что проверить |
|---|---|
| Database error saving new user | Выполнение миграции 001 и логи Authentication/Postgres; ошибку триггера нельзя исправить отключением RLS |
| Profile missing / таблица не найдена | Выполнена ли миграция именно в проекте из `VITE_SUPABASE_URL` |
| Email not confirmed | Открыто ли письмо подтверждения; при необходимости запросите новое |
| Не приходит письмо | Authentication Logs, Custom SMTP, папка «Спам», лимиты отправки и пароль приложения |
| Ссылка ведёт на неправильный адрес | Site URL, сохранённый HTML, порт Vite и перезапуск frontend |
| Ссылка уже недействительна | Используйте самое новое письмо; проверьте срок действия и отключите переписывание ссылок у провайдера |
| Permission denied при изменении role | Ожидаемое поведение: роль не редактируется из frontend |
| Рассылка недоступна | Миграция 002, подтверждённый профиль администратора и серверные настройки из `.env.example` |

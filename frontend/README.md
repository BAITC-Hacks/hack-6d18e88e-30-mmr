# AI Sana — TaskRank & TeamMatch

Frontend MVP: React 19, TypeScript, Vite, Zustand persist и Zod. Русский интерфейс из ветки `alim` объединён с актуальными сервисами Core Platform, аккаунтами и стеклянным профилем из `dev`. Решения и проверки: [INTEGRATION_NOTES.md](../INTEGRATION_NOTES.md); работа команды: [docs/TEAM_WORKFLOW.md](../docs/TEAM_WORKFLOW.md).

## Запуск

Нужен Node.js 24, включая встроенный test runner и `registerHooks` для тестового loader.

После установки frontend- и Python-зависимостей по [корневому README](../README.md) команда `npm start` **из корня** собирает приложение, запускает FastAPI и локальный preview на `http://localhost:5173`. Это production-сборка интерфейса: для авторизации нужны публичные Supabase-настройки до сборки; гостевое демо доступно отдельно. Backend при таком запуске остаётся в локальном development-режиме. `Ctrl+C` останавливает запуск, `BROWSER=none` отключает автоматическое открытие браузера.

Для разработки с обновлением при правках:

```sh
cd frontend
npm ci
npm run dev
```

Откройте `http://localhost:5173`. По умолчанию запросы `/api` идут через proxy Vite к backend на порту 8000. Другой URL задаётся через `VITE_API_BASE_URL` в `frontend/.env.local` (образец `.env.example`); после изменения перезапустите dev server. Ключи AI-провайдера и серверный токен в frontend не передаются.

Backend поддерживает внешний AI и локальный алгоритм с общей тематической политикой. При отсутствии сервера, тайм-ауте или некорректном JSON приложение использует локальное извлечение фактов и уточняющие вопросы. HTTP 4xx и тематические отказы показываются пользователю без обходного fallback. `VITE_AI_MODE=local` позволяет запустить демо без backend.

## Аккаунт и профиль

На `/` и `/auth` открывается экран входа, после авторизации — профиль с именем, email, ролью, статусом подтверждения и настройками рассылки. «Открыть платформу» повторно проверяет сессию и переводит на `/workspace`, задавая начальную роль из аккаунта; из платформы можно вернуться к профилю. Отдельная кнопка «Открыть демо» открывает `/workspace` без регистрации. Переключатель ролей внутри платформы остаётся демонстрационным и не меняет роль аккаунта.

- `src/features/auth/AuthPage.tsx` и `AuthPage.css`: вход, регистрация, подтверждение почты и восстановление пароля.
- `src/features/auth/ProfilePanel.tsx` и `ProfilePanel.css`: текущий аккаунт, подписка, запрос смены пароля и выход.
- `src/services/authClient.ts`: общий клиент авторизации и обработка одноразовых ссылок.
- `src/types/auth.ts`: контракт аккаунта, отдельный от `Team`.

Оформление Aurora Glass использует прозрачные поверхности, `backdrop-filter`, светящиеся границы и CSS-переходы. Для браузеров без blur предусмотрен непрозрачный фон. CSS учитывает системные настройки уменьшения движения и прозрачности. В меню «Дизайн-системы» и на `/design` доступны темы Signal, Atelier и Index; применение меняет оформление аккаунта и платформы. Выбор темы сохраняется отдельно от задач. Шрифты Manrope и Unbounded поставляются локально, лицензии OFL находятся в `public/fonts/`.

Без `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` dev-сервер использует FastAPI и HttpOnly cookie-сессию; в корневом `.env` для него задаётся `AUTH_PROVIDER=local`. В production-сборке авторизация требует обе публичные Supabase-переменные. Ошибка настроенного Supabase не переключает аккаунт на локальную базу. Миграции и настройки: [docs/SUPABASE_SETUP.md](../docs/SUPABASE_SETUP.md); запуск локального API: [backend/README.md](../backend/README.md).

В `frontend/.env.local` допустимы только публичные настройки. SMTP-пароль, секретный ключ Supabase, ключ AI и deployment-токен API не должны попадать в `VITE_*`.

Письма можно посмотреть без отправки:

- http://localhost:8000/email-preview/confirmation
- http://localhost:8000/email-preview/recovery

В локальном режиме предпросмотр использует тот же HTML-шаблон, что и SMTP. Его ссылки демонстрационные. `AUTH_MAIL_FORMAT=html` в корневом `.env` включает HTML и текстовую альтернативу; после изменения нужен перезапуск backend. Supabase Auth использует шаблоны и SMTP из своей панели, независимо от корневого `.env`.

## Реализовано

- Две роли, раздельная навигация, адаптивные экраны и общие компоненты.
- Конструктор: черновик → уточнение → карточка → рейтинг → публикация. Автосохранение, десять редактируемых полей, теги и источники значений.
- Подтверждённый и потенциальный рейтинг по семи категориям, четыре уровня готовности и рекомендации по улучшению.
- Явное подтверждение бизнесом перед публикацией; правка карточки снимает подтверждение и публикацию.
- Каталог с поиском, фильтрами, сортировкой и полными карточками. Опубликованные задачи низкой готовности принимают отклики.
- Рекомендации с объяснением совпадений, профиль команды и личные отклики.
- Форма предложения с проверкой полей, HTTP(S)-ссылок, уникальности ID и активной команды. Одна команда может отправить несколько разных предложений на задачу.
- Обзор бизнеса, рассмотрение и сравнение предложений, независимый ручной выбор нескольких команд.
- Четыре этапа на пару задача/команда с однократным начислением баллов после подтверждения.
- Восемь шагов Demo Mode, сброс с подтверждением, журнал событий.
- AI Inspector: клиентский prompt-контракт, вход, JSON Schema, исходный и используемый ответ, проверка, источник и причина fallback.
- Версионированное сохранение в localStorage, валидация и восстановление повреждённых данных.
- Аккаунт на `/` и `/auth`: регистрация, подтверждение, вход, профиль, сброс пароля и подписка. В разработке доступен SQLite backend, опционально — Supabase; production-экран входа требует Supabase. Демо открывается независимо от аккаунта.

Начальный набор сохраняет примеры обеих веток: **15 задач, 10 команд, 11 откликов**. Рейтинги вычисляются общим сервисом; выбранные команды получают начальные этапы.

## Полный демо-сценарий

Откройте платформу из профиля или гостевое демо с экрана входа, затем включите Demo Mode.

1. **1 Черновик** — откроется пример задачи о прогнозировании спроса.
2. **2 AI** — запустится запрос; после ответа или fallback появятся уточняющие вопросы.
3. **3 Рейтинг** → **Заполнить примерные ответы**. Синтетические ответы отмечены явно, потенциальный рейтинг увеличивается. Фактические баллы начисляются после подтверждения.
4. **Продолжить к карточке** — проверьте десять полей, их источники и рейтинг. Измените поле для демонстрации пересчёта.
5. **Проверить готовность** → отметьте согласие → **Подтвердить карточку** → **Перейти к публикации** → **Опубликовать задачу**.
6. **4 Каталог** показывает задачи; **5 Студент** открывает рекомендации. Общий каталог всегда доступен через навигацию.
7. **6 Отклик** → **Заполнить пример** → **Отправить предложение**.
8. **7 Выбор** — выберите команду вручную. Сравнение нескольких предложений можно показать на исходной задаче Retail.
9. **8 Этапы** — подтвердите Kickoff, затем Prototype. В профиле команды появятся начисленные баллы.
10. Перезагрузите страницу: данные и прогресс сохранятся. **Сброс** → **Отмена** сохраняет состояние; **Сбросить данные** возвращает начальный набор.

Демонстрацию можно начать с середины — используются опубликованные примеры. Публикация, отправка, выбор и подтверждение этапа остаются явными действиями пользователя.

## Правила расчётов

| Категория | Максимум | Состав |
|---|---:|---|
| Контекст и потребность | 20 | По 10 за описание процесса и проблемы |
| Данные | 20 | Полнота подтверждённого описания данных |
| Результат | 15 | Полнота подтверждённого описания результата |
| Критерии успеха | 15 | Полнота подтверждённых критериев |
| Ограничения | 10 | Полнота подтверждённых ограничений |
| Пользователи | 10 | Описание аудитории и сценария |
| Коммуникация | 10 | Контакт 5, формат консультаций 5 |

Уровни: 0–39 — черновик; 40–69 — рабочая; 70–89 — готовая; 90–100 — приоритетная. Это эвристика полноты, которая не подтверждает достоверность бизнес-фактов.

Фактический рейтинг начисляется только за заполненные **подтверждённые** поля. `potentialTotal` показывает баллы уже введённого текста после подтверждения, а не обещает максимальный балл за ещё отсутствующие сведения. При редактировании снимается подтверждение изменённых полей и публикация карточки; баллы неизменённых подтверждённых полей сохраняются. Для публикации нужно повторное подтверждение бизнеса.

Match = технологии × 35% + навыки × 25% + интересы × 20% + отрасль × 20%. Подбор не назначает исполнителя.

Баллы: Kickoff +5, Prototype +10, Validation +15, Final result +20 — всего 50 за проект. Этапы подтверждает бизнес только выбранным командам; повторное подтверждение не начисляет баллы снова.

## Проверки

```sh
npm run build
npm run lint
npm test
```

Domain-тесты проверяют рейтинг, match, роли, подтверждение, публикацию, отклики, выбор нескольких команд, этапы и localStorage. AI-тесты покрывают корректный ответ, заглушку, неверный JSON/схему, HTTP 503, сеть, тайм-аут и отмену. React DOM-тесты проверяют компоненты платформы в StrictMode; отдельные проверки авторизации охватывают локальный и Supabase-клиент.

Тестовый loader компилирует TS/TSX через TypeScript и заменяет CSS пустым модулем; в production он не используется.

`npm test` запускает регрессии ядра и наборы domain, AI, React DOM и Vitest-проверки аккаунтов. Общая команда из корня репозитория — `npm run check` — дополнительно проверяет backend, запуск Uvicorn, SQL-миграции, lint и production build.

При ручной проверке пройдите вход, регистрацию, одноразовую ссылку восстановления, сохранение подписки, переход профиль → платформа → профиль и выход. Проверьте Back/Forward браузера, `/auth/callback`, `/auth/reset-password`, выбор темы на `/design`, клавиатурную навигацию, длинное имя/email и ширины 320, 390 и 1440 px. Фактические результаты текущего объединения записываются в [INTEGRATION_NOTES.md](../INTEGRATION_NOTES.md).

**Ограничение проверки:** браузерная интеграция в текущем сеансе недоступна. DOM-тесты не проверяют визуальный результат, геометрию адаптивной вёрстки и native dialog в конкретном браузере. Перед показом нужно визуально пройти сценарий на desktop и узком экране.

## Структура и границы MVP

`app/` — Zustand и константы; `components/` — общие элементы; `data/` — демонстрационные данные; `features/` — пользовательские сценарии; `services/` — AI, рейтинг, match, сохранение; `styles/` — токены и стили; `types/` — типы; `tests/` — автоматические проверки.

Задачи, команды и отклики находятся в текущем браузере (`ai-sana-taskrank-v1`, версия 2); старые сохранения ядра и `ai-sana-demo` мигрируют. Переключатель ролей — демонстрационный. Аккаунты хранятся отдельно: в SQLite или Supabase Auth и защищённой таблице `profiles`. Переход из профиля не переносит задачи в серверную базу, выход из аккаунта не удаляет демонстрационные данные. Общий CRUD задач и серверная проверка владения ещё требуют реализации. Фактический prompt внешнего провайдера принадлежит backend; Inspector обозначает показанный текст как клиентский контракт.
